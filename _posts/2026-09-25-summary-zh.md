### [Joux–Naccache–Thomé 攻击首次实际伪造 1024 位 RSA 签名](https://eprint.iacr.org/2026/2131.pdf) ⭐️ 9.0/10

一项新发表的密码分析工作首次实际实现了 Joux、Naccache 与 Thomé 于 2007 年提出的算法，在不分解 RSA 模数 N 的前提下，利用对一台硬件安全模块（HSM）的临时签名预言机访问，伪造了 1024 位 RSA 签名。整个攻击耗时约 1380 个 CPU 核心年、跨五个月，并对 HSM 发出了 232 次预言机查询；其中绝大部分时间用于预计算，预计算完成后，攻击者可在离线状态下以约 180 核心年的代价伪造任意签名。作者据此外推：1024 至 4096 位常见 RSA 参数在“拥有签名预言机”这一攻击模型下的实际安全性，比基于整数分解（GNFS）的估计低约 15 至 30 位，即便 4096 位 RSA 也难以在该模型下达到 128 位安全级别。研究以纯黑盒 API 调用冒充 HSM，没有提取其内部密钥；盲签名 RSA 方案同样可提供等价的签名预言机。论文标题亦戏称为 &quot;Nearly SNFS-Speed Signature Forgery Sans Factoring N&quot;。

rss · Lobsters · 9月24日 15:13

**「背景」** RSA 签名安全性传统上被等同于整数分解难度，参数选型一般以通用数域筛法（GNFS）的复杂度为基准。2007 年 Joux、Naccache 与 Thomé 提出了另一条攻击路径：在拥有“原始 RSA 签名/解密预言机”的条件下，可在接近特殊数域筛法（SNFS）的复杂度内伪造签名，而无需分解模数 N。该预言机只需短时间、临时可访问即可，是 HSM、盲签名方案等许多现实部署中存在的真实威胁面。

**「影响」** 在具备临时签名预言机访问能力的攻击者面前，1024–4096 位 RSA 的有效安全强度需下调 15–30 位，使得 4096 位 RSA 也难以在该攻击模型下满足 128 位安全要求。

### [LLM 生成广义规划与 Lean 完备性证明](https://arxiv.org/abs/2609.27105) ⭐️ 8.0/10

近期工作使用大语言模型以 Python 程序的形式自动生成并调试广义规划（能求解某一规划域所有实例的方案），已在多个领域取得完美的测试数据覆盖率，但规划是否真正完备、能否覆盖该域所有实例，只能通过人工评估来判断。本文提出一种方法，可在 Lean 中自动生成广义规划及其相对于输入域约束规范的完备性证明，核心是一种保持语义的 PDDL 到 Lean 转换，并由大语言模型同时生成广义规划及其针对每个满足域约束实例的正式证明，证明正确性由 Lean 内核判定。作者在 13 个常用基准规划域上使用 GPT-5.6-Sol 进行评估，其中 12 个域成功获得了附带有效完备性证明的广义规划，是自动广义规划完备性证明方向的一次重大进展。该方法将 LLM 代码生成与形式化验证相结合，弥补了此前 LLM 生成广义规划缺乏机器可检查完备性证明的不足。

rss · arXiv cs.AI · 9月24日 04:00

**「背景」** 广义规划的目标是计算一个能求解某规划域所有实例的方案，而非仅针对单一实例。PDDL 是经典规划领域的标准建模语言，而 Lean 是一种交互式定理证明器，其可信小型内核可机器化地判定证明是否成立。该工作正是要将 PDDL 描述的规划域、LLM 生成的 Python 或 Lean 广义规划、以及 Lean 中的形式化完备性证明三者结合起来，使正确性可由内核自动验证。

**「影响」** 对从事神经符号方法、LLM 辅助定理证明和经典规划的研究者而言，这一成果首次让 LLM 生成的广义规划具备了机器可检查的完备性保证，在 12/13 的基准域上实现了端到端的形式化验证，是该方向状态的一次实质性推进。

### [Whiteboard \(YC W26\)：面向 AI 编码代理的可视化架构 IDE](https://github.com/devdotfast/whiteboard) ⭐️ 7.0/10

Whiteboard 是由 YC W26 孵化的四人团队 Sid、Alex、Ketan 和 Milan 开源发布的桌面端 IDE，基于 Code OSS 构建，已在 GitHub 以 MIT 许可证开放仓库，并提供 macOS 与 Linux 安装包。工具定位为让人与 AI 编码代理（如 Claude Code、Codex）在同一工作空间中共同进行软件架构设计，核心机制是为代理提供一个 SDK，使其可以在应用内画布上绘制时序图、ER 图等架构可视化内容，而用户在画布上点击这些图表或代理执行轨迹中的片段时，能够跳转到对应的底层代码。项目还内置了一套用 Rust 编写的语义化、AST 感知的 diff 查看器（diffr），可通过 WASM 插件系统自定义规则，并默认将大段新增函数折叠为伪代码、隐藏单元测试和大型文档改动；同时附带“决策日志”，帮助用户追溯代理在执行过程中自主做出的关键决定。当前 Salesforce、Modal 等公司的团队正将其作为架构评审或规约级变更的评审工具使用，搭配 Greptile 等自动代码审查工具时，可在小型改动上跑机器评审、对需要人类判断的改动升级为 Whiteboard 会审。团队表示桌面端将持续保持开源与可自部署，未来计划以托管 Web 版向企业收费，引入会话创建管理、轨迹存储与多人评审等功能。

hackernews · sidharthkmenon · 9月24日 17:21 · [社区讨论](https://news.ycombinator.com/item?id=49833867)

**「背景」** 随着 Claude Code、Codex 等代理式编码工具普及，开发者在享受高产出速度的同时，越来越难以理解并维护由代理自主完成的大量代码变更，这种“认知债”（cognitive debt）使得架构级思考被压缩为纯文本的 Plan Mode，缺乏可视化协作空间。Whiteboard 正是在这一背景下，试图用画布式 IDE 弥合“代理写代码—人类理解系统”之间的鸿沟。

**「影响」** 对于已经在使用代理式工具、需要评审大量 AI 生成代码的开发者与团队，Whiteboard 提供了一个开源、可自托管的本地替代方案，把架构图、语义 diff 与决策追溯整合在基于 VS Code 的环境中，从而改善人机协作的可见性与可控性。

**「社区讨论」** 社区对 Whiteboard 的“伪手绘动画+流式生成图表”效果与整体交互设计给予了正面评价，认为它切实回应了当前 Plan Mode 在高层架构协作上的不足，并期待它能与 GitHub PR 链接评论功能进一步结合。但也有用户指出当前版本仍无法直接编辑文件，并对其能否算作“IDE”提出疑问，提示产品定位和编辑能力仍是需要验证的关键问题。
