### [Strix 安全代理 25 分钟内获取 Baseten 生产 GitHub 管理员权限](https://www.strix.ai/blog/baseten-harbor-github-pat-takeover) ⭐️ 8.0/10

AI 安全公司 Strix 旗下的自动化渗透测试代理，在一个公开的 Docker 镜像构建历史中，发现了 Baseten 内部机器人账户 basetenbot 的有效 GitHub 个人访问令牌（PAT），仅用 25 分钟便获得了该组织生产环境的管理员权限。该令牌具备 Baseten 主产品代码库、驱动生产集群的 GitOps 仓库及 Homebrew 源的主仓库及 push 权限，同时对其他私有仓库（含按客户分库的私有仓库）拥有读写权限。攻击链路完整复现为：定位 Baseten 公开的 Harbor 项目 → 拉取镜像 → 检查构建历史 → 提取处于活跃状态的 GitHub PAT。研究人员于 7 月 13 日深夜上报该令牌及 Harbor 项目信息，Baseten 次日上午将 Harbor 项目设为私有，但研究人员指出令牌本身仍可使用；7 月 14 日 16:34，Baseten 安全团队确认事件为严重级别，并对令牌进行了轮换处理，同时请求安全删除已拉取的镜像。事件详细的技术披露文章已由 Strix 公开。

hackernews · bearsyankees · 9月15日 18:11 · [社区讨论](https://news.ycombinator.com/item?id=49716476)

**「背景说明」** Docker 镜像的构建历史（build history）会保留每一层构建步骤的元数据，包括执行过的环境变量、文件写入和网络请求，因此若在构建过程中临时使用过密钥等敏感凭据，即使后续清理过最终镜像，这些凭据仍可能通过历史层被还原。Harbor 是广泛使用的开源容器镜像仓库，部分企业会将其配置为公开可读，从而可能在不知情的情况下泄露内部构建产物。AI 驱动的渗透测试代理通过自动遍历大量公开镜像并系统性检查其历史层，将这一传统上依赖人工检索的漏洞模式规模化。

**「影响」** 持有该 PAT 的攻击者可对 Baseten 的核心产品仓库、用于集群部署的 GitOps 仓库及其 Homebrew tap 执行管理员级别操作，并访问与客户相关的私有仓库，对 Baseten 的生产环境及客户数据构成严重供应链与代码托管风险。

**「社区讨论」** 社区普遍认可 Baseten 的应急响应流程及时透明，但对其安全姿态表示担忧，同时指出此类问题本质上属于&quot;动机不足的人类不会主动查找，但有意愿的人完全有能力发现&quot;的范畴，因此 AI 代理的核心价值在于以极低的边际成本大规模复现该流程，而非突破人类能力上限；部分评论认为该事件对 Strix 是绝佳营销，对 Baseten 则是负面警示，并就自动化安全测试在未明确授权下的法律边界展开讨论。

### [临床 LLM 智能体：相同评分下隐藏的医嘱级不稳定性](https://arxiv.org/abs/2609.13582) ⭐️ 8.0/10

该论文针对临床场景下的 LLM 智能体提出“同输入重跑”评测方法：在 MedAgentBench 上对 50 个任务、涵盖五类可写入操作（含开立检查、申请药物、转诊等），使用两个 4 位量化、参数规模低于 100 亿的开源模型，在两种温度设置下共执行 1000 次运行，并通过六项可靠性指标比较相同输入下生成的医嘱而非单一得分。结果显示，同一基准分数下不同次运行可能对应实质性不同的医嘱：在 8B 模型、温度 0.7 下，全部 43 个开立检查任务分组在五次相同输入运行中均产生不同医嘱集合，其中 26 组在某些运行下达医嘱、另一些则未下达，28 组记录的编码、剂量或检验项目不同，且其中 22 组的基准均给出相同的失败判定；4B 模型 0.7 下全部 10 个分歧分组亦呈同样现象。研究还发现不同运行的医嘱可能指向不同端点，其中一次执行因服务器拒绝而被记录为失败，但智能体却被告知成功。论文据此建议在临床智能体评测中引入重复运行、动作级稳定性指标以及与执行保真度相匹配的环境反馈机制，但明确指出该研究仅证明“动作级分歧存在并可能被遗漏”，并未给出可泛化的失效率。

rss · arXiv cs.CL · 9月15日 04:00

**「背景」** MedAgentBench 是面向临床场景的智能体基准，其评测方式为单次尝试得分，不检验相同输入是否产生相同动作。LLM 智能体在高风险医疗任务中通常具备开具检查、申请药物和转诊等写权限，因此即便总分一致，动作差异也可能带来临床后果，这一差距正是该工作试图量化的对象。

**「影响」** 在 MedAgentBench 上仅以总分判定临床 LLM 智能体表现会遗漏“评分相同但医嘱不同”的动作级不稳定性，依赖单次得分评估或部署该类智能体的研究与产品方需要将重复运行与动作级稳定性纳入评测流程。

### [开发者称一个月内为 M4 Mac Mini 写出 Linux GPU 驱动](https://codyho.dev/blog/gpu-driver/) ⭐️ 7.0/10

开发者 Cody Ho 声称在一个月内为搭载 Apple M4 芯片的 Mac Mini 编写出一款可工作的 Linux GPU 驱动，方法是在逆向工程 Apple GPU 硬件时借助大语言模型（LLM）来加速分析与代码生成。技术层面，这一驱动填补了 Asahi Linux 在 M3 及之后机型上缺失 GPU 加速支持的关键空白，被部分评论视为 LLM 辅助系统编程的典型用例。然而，社区指出该作者此前因向 Asahi Linux 隐瞒其大量使用 LLM 的情况，以及隐瞒其作为前 Apple 工程师、且与 Apple Silicon 开发人员有直接联系的身份而被该项目封禁。这些未披露的利益冲突，加之 Apple 目前正就所谓被盗商业机密起诉 OpenAI，引发了关于训练数据来源、代码归属以及 Linux 上游是否会接受该驱动的严重担忧。

hackernews · ADevWithAnIdea · 9月15日 19:30 · [社区讨论](https://news.ycombinator.com/item?id=49717638)

**「背景」** Asahi Linux 是一个致力于让 Linux 完整运行在 Apple Silicon（ARM 架构芯片）上的开源项目，长期通过逆向工程方式为较旧的 Apple GPU 开发开源驱动，但在 M3 及更新的硬件上 GPU 加速一直未实现。该项目明确禁止在贡献中使用 LLM 生成代码，以保证所有提交内容的人类可审计性以及上游合规性。

**「影响」** 由于作者身份与 LLM 使用均未对 Asahi Linux 披露，加之与 Apple 既有诉讼及潜在商业秘密问题相关，该驱动很可能无法进入 Asahi Linux 或 Linux 内核主线；用户若想在新版 Apple Silicon 上获得 Linux GPU 加速，更可能依赖带有 AI 辅助代码的第三方分叉，而非上游方案。

**「社区讨论」** 社区对技术成就本身普遍感到印象深刻，认为这展示了 LLM 在替代耗时逆向工程方面的潜力；但主流意见认为，由于作者的前 Apple 工程师背景未披露以及 LLM 训练数据可能涉及被 Apple 指控的 OpenAI 商业机密问题，这份代码极难被 Linux 上游接受，更可能以非官方分叉的形式存在。
