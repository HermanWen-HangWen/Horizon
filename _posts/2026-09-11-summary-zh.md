### [Shopify 将移动应用从 React Native 迁回原生 Swift 与 Kotlin](https://shopify.engineering/back-to-native) ⭐️ 8.0/10

Shopify 宣布将其移动应用从 React Native 迁移回原生 Swift（iOS）与 Kotlin（Android）开发，结束了自 2020 年以来在移动端采用跨平台框架的策略。Shopify 官方给出的理由包括原生开发在性能、工具链和开发者体验方面的提升，以及 LLM 辅助代码生成显著降低了维护两套独立原生代码库的成本，使原本被认为不经济的迁移变得可行。该决策意味着 Shopify 重新认可了专门的原生 iOS 与 Android 团队对优化各平台体验的价值。

hackernews · fnthawar2 · 9月10日 14:09 · [社区讨论](https://news.ycombinator.com/item?id=49643982)

**「背景」** Shopify 在 2020 年将移动应用转向 React Native，目的是让前端 Web 开发者能够跨平台贡献移动端代码，从而提高团队复用率和开发效率。React Native 长期以来被许多公司采用以共享单一代码库，但其性能瓶颈、平台差异处理和原生功能集成等痛点也广受讨论。近年来，大语言模型在生成原生 Swift 和 Kotlin 代码方面的能力显著提升，使独立维护两个原生代码库的边际成本大幅下降。

**「影响」** Shopify 作为大规模生产级应用公开放弃 React Native 并回归原生开发，可能为其他考虑跨平台方案的团队提供重要参考，尤其在 AI 辅助开发改变了多代码库维护成本的前提下。

**「社区讨论」** 讨论中出现明显分歧：部分长期从事原生 iOS 开发的工程师对这一决策表示强烈认同，认为专业原生团队对各平台优化至关重要；也有用户分享了借助 Codex 等 LLM 工具在数小时内将中型 React Native 应用迁移到 Swift/Kotlin 的实际经验。不过，有参与者指出，即使没有 LLM 辅助，中等规模 React Native 应用的迁移也已经在进行中，因此质疑将迁移可行性主要归因于 AI 的说法。

### [Forgejo 16.0.3 及更早版本存在严重 RCE 漏洞，需升级至 16.0.4](https://codeberg.org/forgejo/forgejo/src/branch/forgejo/release-notes-published/16.0.4.md) ⭐️ 8.0/10

Forgejo 发布安全更新 v16.0.4，修复了一个影响 v16.0.3 及更早版本的严重远程代码执行（RCE）漏洞。该漏洞位于模板仓库初始化流程中：当用户基于一个模板仓库新建仓库时，Forgejo 会先克隆模板仓库、删除其 .git 目录，然后对 .forgejo/template 中列出的文件执行变量模板替换，最后再初始化一个新的 git 仓库。如果模板仓库的内容未受信任，模板展开过程会被干扰并被诱导在服务器上执行任意代码。该问题已通过 PR \#14301 修复，官方强烈建议所有运行 Forgejo 的实例立即升级到 v16.0.4，以避免被恶意模板触发 RCE。

hackernews · weierstass · 9月10日 15:57 · [社区讨论](https://news.ycombinator.com/item?id=49645907)

**「背景说明」** Forgejo 是一个面向自托管场景的 Git 平台分支，从 Gitea 社区分叉而来，常被用于企业内部或开源项目的代码托管。所谓“模板仓库”是 Forgejo 提供的一项功能，允许用户把一个仓库作为模板，通过模板变量替换快速生成结构一致的新仓库。

**「影响评估」** 任何对外开放、允许用户基于他人模板仓库创建新仓库的 Forgejo 实例（≤16.0.3）都可能被精心构造的模板仓库利用，从而在服务器上执行任意代码。

**「社区讨论」** 社区普遍认为这是一个严重且应被尽快修复的问题。Gitea 项目维护者 techknowlogick 表示 Gitea 不受同一漏洞影响，并提醒不应因此类事件指责报告者。也有评论者担心 Forgejo 此前禁止 LLM 贡献的政策，可能导致漏洞排查与发现上处于不利位置。

### [MERIT：评估长期记忆对工具调用 LLM 代理的边际效用与成本](https://arxiv.org/abs/2609.05441) ⭐️ 8.0/10

MERIT \(Memory Evaluation for Realistic Instrumented Tasks\) 是一个用于评估长期记忆在工具调用 LLM 代理中作用的基准测试与执行框架，它以显式成本核算衡量记忆的边际效用。MERIT 在三个领域提供情节式工具调用任务，通过自动泄露检查验证任务对早期情节事实的依赖性，包含以更新事实回忆为终点的难度阶梯、 受控的记忆损坏机制以及对每次记忆操作的完整 token 与美元计量。在 23,440 个评分情节（约 42.57 美元）中，先导实验在 gpt-4.1-mini 上完成，并采用 GPT-4.1 与 Claude Haiku 4.5 进行 3 模型 × 3 种子的预注册网格测试（记忆侧固定），结果显示记忆将依赖记忆任务的成功率从经泄露验证的 0.00 基线提升至 0.55–1.00。在更新事实场景下，嵌入检索表现不稳定（模型间 0.30–0.95，最大种子差距 0.45），代理在正确检索到值后仅有 55% 的概率据此采取行动；而写时更新型存储（结构化事实存储，尤其是 LLM 摘要）维持在 0.70–1.00，但混合方案反而不如纯事实存储。一项以完整重放对照为前置条件的 Claude Sonnet 5 最新代际抽检复现了上述模式。研究还表明，仅替换记忆实现即可使任务成功率变化高达 60 个百分点，且完整重放从不具备经济性：每领域最佳条件可带来 2.7–3.9 倍的每美元边际效用。

rss · arXiv cs.AI · 9月10日 04:00

**「背景说明」** 现有针对 LLM 代理长期记忆的评估主要依赖 LoCoMo、LongMemEval 等对话回忆类基准，衡量的是对对话历史的问答能力，而非记忆内容是否真正改变了代理的工具调用行为。MERIT 试图填补这一方法论空白，将评估从“能否回忆”转向“在显式成本约束下，记忆是否带来可计量的任务收益”。

**「影响」** 该基准为构建记忆增强代理的开发者提供了实证依据：单纯依靠嵌入检索并不可靠，写时更新型结构化存储或 LLM 摘要方案在更新事实任务上更具性价比，而完整重放历史上下文在 MERIT 的成本计量下始终不经济。

**标签**: `#LLM agents`, `#long-term memory`, `#benchmark`, `#tool use`, `#evaluation methodology`

### [ARC-Bench:冻结 JEPA 世界模型中闭环重规划掩盖了动作排序缺陷](https://arxiv.org/abs/2609.05461) ⭐️ 8.0/10

ARC-Bench 研究针对冻结 JEPA 世界模型在无奖励潜空间规划中广泛采用的&quot;潜空间距离可作为动作排序依据&quot;这一隐含假设,设计了无泄露、固定候选动作的评测协议,在官方发布的 JEPA-WM 检查点上对导航与操控类控制任务进行审计。实验发现该假设存在严重且结构性的失败:在官方操控审计中,评分最高的候选动作几乎总是次优的,迷宫类任务中也出现同样的逆序现象。将视觉骨干替换为 V-JEPA 1 与 V-JEPA 2\(ViT-L/ViT-G 规模\)等视频预训练编码器后,该缺陷依然存在,而来源、欠训练、匹配预算的骨干对照以及度量循环性对照均排除了平凡解释。研究进一步揭示缺陷长期未被察觉的原因在于闭环重规划的掩盖效应:降低规划器重规划频率后,导航与操控任务的成功率均出现崩塌,而被频繁重规划所挽救的回合在 PointMaze 首规划诊断中富集了严重的首规划排序失败。因此,闭环成功率会系统性高估冻结潜空间表示的可排序性,ARC-Bench 同时提供了度量方法与对掩盖机制的解释,为在冻结潜空间规划器之上进行适配、摊销或重规划的方法敲响了警钟。

rss · arXiv cs.AI · 9月10日 04:00

**「背景」** JEPA 类世界模型通过预测未来表征来辅助规划,其中常见的&quot;无奖励潜空间规划&quot;做法是在冻结的潜空间中,用候选动作对应的预测未来嵌入与目标嵌入之间的距离来给动作打分,选出距离最近者。这隐含要求潜空间距离与真实代价的排序一致,即潜距离排名应等同于真实代价排名,这一前提此前并未被系统性地直接审计。

**「影响」** 基于冻结 JEPA-WM 的潜空间规划在缺乏直接动作排序审计时,其闭环成功率会被系统性高估,从而影响依赖此类规划器的决策与控制方法的可靠性评估。

### [选项-评判框架中选项冗余与策略坏死分析](https://arxiv.org/abs/2609.05508) ⭐️ 8.0/10

论文《When Do Options Help? Policy Necrosis and Redundant Coverage in Option-Critic》对分层强化学习中经典的 Option-Critic 框架提出了系统的理论批评。作者指出，Option-Critic 学到的终止规则实际上贡献甚微：当终止判据与选择选项的策略读取相同的值时，终止测试会在每一步都触发，使学到的规则退化为“始终终止”；而在 Option-Critic 自身的设置中（选择策略探索、终止规则不探索），终止规则反而会阻塞探索，存在使其承受 Ω\(T\) 遗憾而“始终终止”策略只有 O\(log T\) 遗憾的情形，但强制每步终止并不损害“选项越多性能越好”的曲线。论文进一步指出，单个选项内部的策略几乎不进行探索，会使状态在首次遇到看起来不错的动作后就锁定并停止更新，作者称之为“策略坏死”（policy necrosis），并给出了状态级检测方法，在典型选项中约五分之三的状态呈现坏死状态；恢复探索后这些状态得到修复，单个选项即可完成任务。最后，作者发现增加选项数量并未改善任何单个选项的性能，真正下降的是所有选项在同一状态同时失败的联合概率，从 59% 降至 4%，整体性能随之变化。

rss · arXiv cs.LG · 9月10日 04:00

**「背景」** Option-Critic 是一类端到端学习分层强化学习的方法，它同时学习一组“选项”（子策略）以及何时将控制权交还给上层的终止规则，常被宣传为“选项越多性能越好”。该论文针对其声称的优势进行解构，聚焦于终止规则和选项内部策略两个核心组件，并借助遗憾界理论分析与 Four Rooms 等典型实验揭示其机制缺陷。

**标签**: `#Hierarchical Reinforcement Learning`, `#Option-Critic`, `#Exploration`, `#Reinforcement Learning Theory`, `#Research Critique`

**「背景」** 协作推测解码（CoSD）是一种分布式 LLM 推理范式，由设备端的小模型先草拟若干候选 token，再交给服务器端的大模型进行验证和纠错，从而在保持大模型输出质量的前提下提升整体吞吐。当设备端 SLM 与服务器 LLM 使用不同词表（heterogeneous vocabularies）时，常规的残差重采样需要把草拟分布与目标分布对齐后再回传，会产生大量跨网络通信，在边缘-云场景中成为关键瓶颈。

### [Lakebase Postgres 通过扩大共享缓冲与 HugeTLB 提升计算缓存](https://www.databricks.com/blog/improving-lakebase-postgres-compute-cache) ⭐️ 7.0/10

**「背景」** Lakebase Postgres 采用存算分离架构，计算节点需要在 DRAM 中缓存来自对象存储的热点页，传统方案由共享缓冲加内核页缓存两层组成。作者指出这种方案存在双重缓冲浪费、共享缓冲固定且通常较小（上限约 1 GB）、以及每后端进程独立维护页表等问题，在大工作集下大量命中只能落到较慢的本地文件缓存（LFC），并因页表膨胀和 TLB 未命中带来显著开销。

**「方案」** 团队选择在固定规格计算上先推进改造，将共享缓冲提升至 DRAM 的 75% 并停用 LFC，使热点页直接留在最快层级，同时避免双重缓冲并为后续引入数据库感知的替换策略留出空间。针对进程级架构带来的页表膨胀，他们启用显式 HugeTLB（2 MB）大页：在大页机制下，32 GB 共享缓冲对应的页表从约 32 GB 降至很小量级，TLB 未命中率显著下降，内部基准测得尾读延迟降低约 40%、CPU 利用率下降约 30%。由于 Lakebase 运行在裸金属上的轻量级客户机 VM 中，大页必须在宿主机预留、虚拟机监控器背衬以及客户机内核三层一致，否则任何一层退化都会削弱收益，因此团队在 VM 基础设施中专门引入并串联这三层的 2 MB HugeTLB 支撑，并在启动后回收多余大页。生产实测方面：8 月 11 日某大端点上 Postgres 块访问量翻倍、存储层 GetPage/s 从约 8K 降至约 1.5K；8 月 14 日另一端点吞吐上升约 43%，缓存命中率近 100%；8 月 15 日某工作负载 CPU 从 20 核降至 4 核，吞吐也达到两倍。作者也坦承这些数字来自特定生产端点、未公开工作负载和基线细节，并明确后续要把动态共享缓冲扩展到自动伸缩计算，需要随扩缩动态调整共享缓冲与对应大页数量，相关实现细节留给第二篇博文。

**「启示」** 作者的核心论点是：在存算分离的 Postgres 中，缓存效率同时受共享缓冲容量和地址翻译开销制约；把共享缓冲推到 DRAM 的 75% 并在 VM 全栈启用显式 HugeTLB，是当下最务实的提速路径，而真正的终态则是支持随工作负载自动伸缩的动态共享缓冲。
